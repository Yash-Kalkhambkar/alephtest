## 1. Recommended Python architecture

### 1.1 Shape: a small pipeline of pure functions, wrapped by a thin API

```
 generate_data.py ──► data/stands.csv, data/flights.csv
                              │
                       loader.py        (read CSV → raw rows + line numbers)
                              │
                       validation.py    (raw rows → typed Stand/Flight + DataIssue list)
                              │
                       allocation.py    (valid flights + stands + buffer → Allocation list)
                              │
                       metrics.py       (allocations + stands + window + issues → metrics)
                              │
                       service.py       (runs the pipeline once → PipelineResult)
                              │
                       api.py           (FastAPI: 4 GET endpoints read PipelineResult)
```

**Why:**
- The PDF demands separate files for generation, loading/checks, allocation, metrics, API (M-20).
- Each stage is a **pure function** (inputs in, outputs out, no globals, no I/O except `loader` and `generate_data`). That makes unit tests trivial, and makes live changes in the follow-up call easy: you change one function and its test.
- The API only *reads* a precomputed result. All business logic is outside FastAPI, so it is testable without HTTP and replaceable (Flask, CLI) without touching it.
- Computing once at startup is enough because the data is static CSV and the result is deterministic. No cache invalidation, no database, no concurrency problems.

### 1.2 Libraries

| Need | Choice | Why |
|---|---|---|
| Web API | FastAPI + uvicorn | Required/allowed by the PDF; typed response models; free interactive docs at `/docs` |
| CSV | stdlib `csv` (`DictReader`) | Gives exact row/line numbers and full control over malformed rows. `pandas` would hide bad rows (silent coercion to `NaN`) and is a heavy dependency for ~60 rows |
| Models | stdlib `dataclasses` + `enum` | Domain stays free of web framework; trivial to read |
| API schemas | `pydantic` models (comes with FastAPI) | Only at the API boundary, to shape/validate responses |
| Time | stdlib `datetime` / `timezone.utc` | Enough; no `pytz`/`pandas` needed |
| Tests | `pytest`, `httpx` (FastAPI `TestClient`) | Required; `httpx` is needed by `TestClient` |

`requirements.txt` (no code, just the names): `fastapi`, `uvicorn`, `pytest`, `httpx`. Pin minor versions when writing the file.

### 1.3 Style rules

- Type hints everywhere; `from __future__ import annotations` not required on 3.10.
- Functions ≤ ~25 lines where possible; one responsibility each.
- No bare `except`; custom exceptions for fatal data errors.
- No global mutable state except the single `PipelineResult` stored on `app.state`.
- Use `logging` (not `print`) for startup info (rows read, issues found, buffer used).

## 4. CSV loading and validation strategy

### 4.1 Two-step: *load* then *validate*

1. **`loader.py`** only reads the file. It yields raw string rows with the original **line number** (header = line 1, first data row = line 2). It uses `encoding="utf-8-sig"` to tolerate a BOM. It does no judging of values.
2. **`validation.py`** judges each raw row and produces either a typed object or a `DataIssue`.

**Why split:** the PDF lists "data loading and checks" in one bullet, but separating *reading* from *judging* means tests for validation need no files at all (pass in-memory rows), and file-handling errors stay in one tiny place.

### 4.2 File-level problems are fatal; row-level problems are not

| Problem | Behaviour | Why |
|---|---|---|
| File missing / unreadable | Raise `DataFileError`; app fails fast at startup with a clear message | Nothing can be planned without data; a half-running API would mislead planners |
| Header missing a required column (or empty file) | Raise `DataFileError` naming the missing columns | We cannot interpret any row |
| Unknown *extra* columns | Ignored, logged once | Real feeds grow columns; ignoring is harmless |
| A bad **row** | Never fatal. Reported as `DataIssue`, then dropped or fixed | The PDF: real data is messy; bad rows must be caught, not crash the system |

### 4.3 Where rules live

- Row-level rules: `validate_flight_row(...)` and `validate_stand_row(...)` (pure; take the raw row, settings, and the set of already accepted ids).
- File-level orchestration: `validate_flights(rows, settings)` and `validate_stands(rows)` loop over rows, collect valid objects + issues, and count `rows_read`.
- Timestamp parsing: one helper `parse_utc_timestamp(text)`, the only place that touches timezone logic (§6).

## 5. Handling of malformed records

### 5.1 Principle: **fix only what is provably safe; drop everything else; report all of it**

**Why:** guessing in a safety-relevant planning tool is worse than dropping. A wrong guessed time could create a wrong (but "valid-looking") allocation, which a planner would trust. A dropped, clearly reported row is a visible, fixable problem.

### 5.2 Flight row checks (evaluated in this order; first failure wins)

| # | Check | Issue code | Action | Message example (planner-readable) |
|---|---|---|---|---|
| 0 | Wrong number of columns | `MALFORMED_ROW` | DROPPED | "Row has 3 columns, expected 4." |
| 1 | Normalise: trim whitespace, uppercase `flight_id` and `aircraft_size` | `VALUE_NORMALISED` | FIXED (only recorded if the row survives) | "Aircraft size ' m ' normalised to 'M'." |
| 2 | Required value present (`flight_id`, `aircraft_size`, `arrival_time`, `departure_time`) | `MISSING_VALUE` | DROPPED | "Departure time is missing." |
| 3 | `aircraft_size` ∈ {S, M, L} | `INVALID_AIRCRAFT_SIZE` | DROPPED | "Aircraft size 'XL' is not supported (allowed: S, M, L)." |
| 4 | Both timestamps parse as ISO 8601 **with** timezone | `MALFORMED_TIMESTAMP` | DROPPED | "Arrival time '15/01/2027 7pm' is not a valid ISO 8601 UTC timestamp." |
| 5 | `departure > arrival` (strictly) | `DEPARTURE_NOT_AFTER_ARRIVAL` | DROPPED | "Departure 08:50Z is not after arrival 09:20Z." |
| 6 | `window_start <= arrival < window_end` | `OUTSIDE_PLANNING_WINDOW` | DROPPED | "Arrival 05:10Z is outside the planning window 06:00Z–12:00Z." |
| 7 | `flight_id` not already **accepted** | `DUPLICATE_FLIGHT_ID` | DROPPED (first kept) | "Flight ID 'AX798' already used by row 4; this row ignored." |

**Why first-failure-wins:** one row → one issue keeps `rows_read = valid + dropped` trivially true and the report short. The trade-off (a row with two problems reports only the first) is stated in the README and acceptable at this scale.

**Why the missing-ID case sits under `MISSING_VALUE`:** one code with a `field` attribute covers all "blank cell" cases without code-explosion; `field` tells the planner which one.

### 5.3 Decisions on edge cases

| Case | Decision | Why |
|---|---|---|
| Departure **==** arrival (zero ground time) | Drop (`DEPARTURE_NOT_AFTER_ARRIVAL`) | An aircraft with zero ground time is almost certainly a data error; keeps interval maths strictly positive |
| Arrival inside window but departure after 12:00 | **Keep** | The window defines which *arrivals* we plan; aircraft leaving later still occupy the stand (assumption A3) |
| Arrival outside window | Drop with reason | Matches the PDF metric wording "valid flights arriving 06:00 to 12:00"; keeps scope unambiguous (A3) |
| Duplicate `flight_id` | Keep the first, drop later ones, report both ids/rows | Deterministic and explainable; "first in file wins" (A5) |
| Earlier row with same id was itself invalid | Not a duplicate (compared to *accepted* ids only) | Otherwise one bad row would wrongly poison a good one |
| Naive timestamp (no `Z` / offset) | Drop as `MALFORMED_TIMESTAMP`, message says "no timezone" | The PDF says all times are UTC, but a naive value cannot be proven to be UTC; do not guess |
| Timestamp with another offset (e.g. `+02:00`) | Accept and convert to UTC | Unambiguous, correct, harmless |
| Fully blank line in CSV | Skipped by the csv reader (not a record) | A blank line is not a flight; documented in README |
| Lower-case / padded values | Normalise + report as `FIXED` | Safe and lossless; still not silent |

### 5.4 Stand row checks

| Check | Code | Action |
|---|---|---|
| Column count | `MALFORMED_ROW` | DROPPED |
| Missing `stand_id` / `stand_type` / `max_size` | `MISSING_VALUE` | DROPPED |
| `stand_type` ∈ {PLB, REMOTE} | `INVALID_STAND_TYPE` | DROPPED |
| `max_size` ∈ {S, M, L} | `INVALID_STAND_SIZE` | DROPPED |
| Duplicate `stand_id` | `DUPLICATE_STAND_ID` | DROPPED (first kept) |
| Normalisation (trim, uppercase) | `VALUE_NORMALISED` | FIXED |

**Why validate stands too:** the PDF only breaks flights on purpose, but a bad stand row would silently corrupt every allocation. Same "never silent" principle, cheap to implement with the same helper.

### 5.5 Sample `flights.csv` bad rows (generator inserts these at fixed positions)

| Kind | Code | Origin |
|---|---|---|
| Departure before arrival (`CZ411`) | `DEPARTURE_NOT_AFTER_ARRIVAL` | PDF |
| Invalid size (`DL902`, `XL`) | `INVALID_AIRCRAFT_SIZE` | PDF |
| Missing departure (`EV318`) | `MISSING_VALUE` | PDF |
| Unparseable timestamp | `MALFORMED_TIMESTAMP` | Ours |
| Duplicate ID (inserted *after* its original) | `DUPLICATE_FLIGHT_ID` | Ours |
| Arrival before window start (`05:10Z`) | `OUTSIDE_PLANNING_WINDOW` | Ours |
| Blank `flight_id` | `MISSING_VALUE` | Ours |
| `" ax500 "`, `" m "` | `VALUE_NORMALISED` (FIXED, flight remains valid) | Ours |

That is 6 distinct dropped codes + 1 fixed code (≥ 5 required).

## 6. Timestamps and UTC

### 6.1 Rules

- Internal representation: **timezone-aware `datetime` in UTC**. Never naive.
- Parse: ISO 8601. Note for implementation: Python 3.10's `datetime.fromisoformat` does **not** accept a trailing `Z`; replace `Z` with `+00:00` before parsing (or use `strptime` with an explicit format). Python 3.11+ accepts `Z`, but the project must work on 3.10.
- Convert any offset to UTC after parsing.
- Output: ISO 8601 with `Z`, seconds precision (`2027-01-15T06:05:00Z`), produced by one formatting helper used by all API schemas.
- Durations: whole minutes via `timedelta`; the buffer is a `timedelta` built from the configured minutes.

**Why:** timezone bugs are the classic silent failure in scheduling software (and one of the AI-debugging examples the PDF gives). One parse function and one format function leave a single place to get it right.

## 7. Stand allocation algorithm and its limitations

### 7.1 Chosen method: deterministic greedy, first-come-first-served by arrival

**Pre-sort** valid flights by `(arrival_time, departure_time, flight_id)`. For each flight in that order:

1. **Compatible stands** = stands with `stand.max_size >= flight.aircraft_size`.
   - If none exist at all → `UNASSIGNED / NO_COMPATIBLE_STAND`.
2. **Free stands** = compatible stands where the buffer-aware conflict check passes (§9).
   - If none are free → `UNASSIGNED / NO_STAND_AVAILABLE`.
3. **Pick** the free stand with the lowest ranking key:
   `(0 if PLB else 1, stand.max_size, stand_id)`
   i.e. **PLB first → smallest sufficient size → stand id alphabetical**.
4. Record the assignment and update that stand's "last departure".

### 7.2 Why greedy (and not something smarter)

| Alternative | Why not here |
|---|---|
| Optimal (ILP / interval-graph colouring / max-flow) | Not expected ("Find the best possible allocation" is explicitly *not* required); heavy dependency; hard to explain in an interview; hard to change live |
| Random / heuristic search | Not deterministic or explainable |
| **Greedy by arrival** | Natural for operations (earliest arrival decides first, like a real queue), O(F × S), ~25 lines, deterministic, easy to explain, easy to change live |

### 7.3 Why PLB first

Preferences, in the PDF's words: *"Use PLB stands as much as you can"* and *"Leave as few flights unassigned as you can."* Putting PLB first in the ranking key is the simplest way to honour the first preference **without** ever violating a hard rule, because ranking only orders stands that have already passed the hard-rule filters.

Important subtlety: PLB-first only chooses **among free stands**. A flight is **never left unassigned while any compatible stand is free** (it would fall back to a remote stand). So the "few unassigned" preference is respected at each step; PLB preference is applied second. This is stated in the README as the order of priorities: *hard rules → assign if at all possible → prefer PLB among the options.*

### 7.4 Why "smallest sufficient size" as the second key (best-fit)

Without it, a small aircraft could take the only L-capable PLB, and a large aircraft arriving a minute later would have nowhere to go. Picking the smallest stand that fits keeps large stands available for large aircraft. It is a standard, one-line, easy-to-explain rule.

### 7.5 Why `stand_id` as the last key

It removes ties, so two runs always agree (AC-08), and it is predictable for testing and for live demonstrations.

### 7.6 Unassigned handling

| Reason code | Meaning | Message template |
|---|---|---|
| `NO_COMPATIBLE_STAND` | No stand in the dataset is large enough for this aircraft (e.g. only S stands loaded) | "No stand can take size {size}." |
| `NO_STAND_AVAILABLE` | Compatible stands exist, but all are occupied or inside the turnaround buffer at arrival | "All {n} stands that can take size {size} are occupied or within the {buffer}-minute turnaround buffer at {arrival}." |

**Why two codes:** they have different fixes for a planner: the first means "infrastructure/data problem", the second means "capacity/timing problem". The message makes the reason readable without opening the code.

Unassigned flights are **not retried**, **not bumped into a different time**, and **do not displace** earlier flights. Simplicity over optimality (see limitations).

### 7.7 Limitations (to repeat in the README)

1. **First come, first served is myopic.** An early long-stay aircraft can block a stand that many later short-stay aircraft could have shared.
2. **PLB-first may be locally good but globally poor.** Taking a PLB now may cause a later flight to be unassigned that a different choice would have fitted.
3. **No look-ahead or backtracking**, so the result is not optimal for either preference.
4. **No priority** between flights (airline, passenger count, delay). All are treated equally.
5. **Does not minimise remote bussing time**, only counts PLB vs remote.
6. **Ties and ordering are arbitrary but deterministic**; a different but equally reasonable rule would give a different allocation.

### 7.8 One example the algorithm handles badly (for the README, fully worked)

Only one PLB stand `C03` (M) is in play.

| Flight | Size | Arrival | Departure |
|---|---|---|---|
| F1 | M | 06:00 | 10:00 (4 h) |
| F2 | M | 06:10 | 06:50 |
| F3 | M | 07:10 | 07:50 |
| F4 | M | 08:10 | 08:50 |

Greedy (by arrival) gives the PLB to F1 for 4 hours. F2–F4 go remote. **1 of 4 flights on PLB.** If F1 had gone remote, **3 of 4 flights** (F2, F3, F4) could have used the PLB with 15-minute gaps (06:50→07:10 = 20 min OK, 07:50→08:10 = 20 min OK). Greedy cannot see this because it never looks ahead. A fix (not implemented, for "next steps"): rank PLB candidates by *stay length* or run a small improvement pass.

## 8. Aircraft-to-stand size compatibility

- Order: `S < M < L` via `IntEnum`.
- Rule: stand accepts aircraft iff `stand.max_size >= aircraft.aircraft_size`.
- Implemented as one tiny function `can_fit(flight, stand)` with its own tests (H2).
- Table of truth:

| Aircraft \ Stand max | S | M | L |
|---|---|---|---|
| S | ✅ | ✅ | ✅ |
| M | ❌ | ✅ | ✅ |
| L | ❌ | ❌ | ✅ |

**Why a standalone function:** it is the most "business-critical" one-liner in the project (H2); isolating it lets a test pin all 9 combinations and lets an interviewer change it (e.g. add `XL`) in seconds.

## 9. 15-minute turnaround implementation

### 9.1 Definition

A flight `b` may follow flight `a` on a stand iff

`b.arrival_time >= a.departure_time + turnaround_buffer`

- Exactly equal **is allowed** (a 15:00 departure and a 15:15 arrival are fine with a 15-minute buffer). This matches the PDF's "at least 15 minutes".
- Less than the buffer, even by one second, is a conflict.
- The buffer is **applied on the stand timeline only** (between consecutive occupants). It is not added before the first flight and not required after the last.

### 9.2 Why checking only the last flight on a stand is correct

Flights are processed in non-decreasing arrival order, and stands never hold overlapping flights. Therefore, the most recently assigned flight on a stand always has the **latest departure** on that stand, and every earlier flight finished before it started. So a new flight conflicts with the stand **iff** it conflicts with that last flight. This reduces the check to a single comparison per stand, and keeps the code very short.

**Caveat:** this shortcut depends on the sort order. The independent checker (`find_violations`, §9.3) does not rely on it, and the README should state this dependency.

### 9.3 Independent hard-rule checker

`find_violations(allocations, buffer) -> list[str]` re-checks the **finished** result from scratch: group by stand, sort by arrival, verify (H2) size fit, (H1) no overlap, (H3) buffer gap for every consecutive pair. It does not reuse the allocator's shortcut.

- Used in tests on the sample data and on every scenario.
- Also called once at startup; a non-empty result raises an error (fail fast).

**Why:** "Rules must never be broken" is the project's central promise. A second, independent implementation of the rules is the cheapest way to *prove* the promise, and it is easy to explain.

### 9.4 Configuration

The buffer lives in `config.py` as `TURNAROUND_BUFFER_MINUTES = 15`, overridable by environment variable (§11). No other file contains the number 15 (AC-16). Edge: `0` is allowed (back-to-back), negative values are rejected at startup.

## 10. Metrics calculation strategy

### 10.1 Scope for all allocation metrics

**Scope:** *all valid flights whose `arrival_time` ∈ [06:00, 12:00) UTC on the planning date* (invalid rows are excluded; they are covered by the data-quality metric). Because invalid/out-of-window rows are dropped at validation, "all valid flights" = "all flights that were allocated".

### 10.2 Metrics (5 allocation metrics + 1 data-quality block; ≥ 4 required)

| # | Metric | What it measures | Formula | Flights / window covered | Why a planner cares |
|---|---|---|---|---|---|
| 1 | **Assignment summary** (`total_valid_flights`, `assigned`, `unassigned`, `unassigned_rate`) | How many valid flights got a stand | `unassigned_rate = unassigned / total_valid` (0 if none) | All valid flights arriving 06:00–12:00 | Unassigned aircraft are the most serious outcome: they need a manual solution or must be delayed |
| 2 | **PLB usage** (`flights_on_plb`, `flights_on_remote`, `plb_rate_of_valid`, `plb_rate_of_assigned`) | Share of flights served by a loading bridge | `plb_rate_of_valid = on_plb / total_valid` | All valid flights arriving 06:00–12:00 | PLB is preferred by passengers and airlines; remote costs more and is slower. This is the main quality number for the PLB preference |
| 3 | **Unassigned breakdown** (by reason, by aircraft size) | Why/which flights failed | counts | Unassigned flights in the same set | Separates *capacity problems* from *data/infrastructure problems*; shows if large aircraft suffer most |
| 4 | **Stand utilisation** (per stand and per type) | Share of the window each stand is occupied | `occupied_minutes / window_minutes (360)`; occupied minutes = assigned flights' ground time **clipped to the window end**; buffers **not** counted | Assigned flights; window 06:00–12:00 | Shows idle vs overloaded stands; supports decisions on adding/closing stands |
| 5 | **Peak concurrency** (`aircraft_on_ground`, `first_occurred_at`, `stand_count`) | Highest number of valid aircraft on the ground at once (assigned or not) | Sweep over arrival/departure events within the window | All valid flights; window 06:00–12:00 | Compares demand to total stands: if peak > stands, unassigned flights are unavoidable |
| 6 | **Data quality** (`rows_read`, `valid`, `dropped`, `fixed` per file) | Trustworthiness of the input | counts from the issue list | All rows of both files | Tells the planner how much to trust the numbers and what to fix upstream |

**Why these:** each answers a different planner question (*Did everyone get a stand? How good were the stands? Why did some fail? Are resources balanced? Was it ever impossible? Can I trust the data?*), is computable from plain lists with a few lines, and is easy to verify by hand in tests.

### 10.3 Details

- Ratios rounded to 4 decimals **in the API layer only** (compute with full precision).
- Division by zero → `0.0`, never an exception (e.g. empty valid set).
- Peak concurrency uses departure-before-arrival ordering at identical timestamps (an aircraft leaving at 09:00 and one arriving at 09:00 are not counted as simultaneous), consistent with half-open intervals `[arrival, departure)`.
- Utilisation per type = unweighted mean of that type's per-stand utilisations (simple, explainable).

## 11. Configuration management

All settings and constants live in **one** module, `config.py`, as a frozen `Settings` dataclass plus a few named constants.

| Setting | Default | Purpose |
|---|---|---|
| `turnaround_buffer_minutes` | `15` | Hard rule H3 (env `TURNAROUND_BUFFER_MINUTES`) |
| `planning_date` | `2027-01-15` | Day of the plan (env `PLANNING_DATE`, ISO date) |
| `window_start_utc` / `window_end_utc` | `06:00` / `12:00` on `planning_date` | Planning window (derived from date + start/end hour constants) |
| `data_dir`, `stands_file`, `flights_file` | `data/`, `stands.csv`, `flights.csv` | Paths (env `DATA_DIR`) |
| `random_seed` | `42` | Generator seed |
| `generated_valid_flights` | `48` (+1 normalisable) | Generator size (tune after first run) |
| `size_mix` | S 30%, M 50%, L 20% | Generator size distribution |
| `ground_time_minutes_by_size` | S 30–60, M 45–90, L 75–150 (5-min steps) | Generator ground times |
| `arrival_peak` | 40% of arrivals in 08:00–09:30, 60% uniform | Generator arrival spread |
| `size_order`, enum values | in `models.py` | |

**Why one module:** the PDF asks for "no unexplained magic numbers" and "settings … in one obvious place". A reviewer (or interviewer) can find every knob in one file.

**Why env overrides for only buffer/date/data dir:** those are the knobs a planner or live-demo might turn; the rest are generator parameters that rarely change.

**How tests use it:** functions take `settings` (or the buffer) as a **parameter**, so tests pass their own values and never mutate global state.

**Validation at startup:** buffer is an integer ≥ 0; window end after start; otherwise fail fast with a clear message.

### 11.1 Sample-data rationale (for README §3)

- **11 stands, 6 PLB (L, L, M, M, M, S) + 5 remote (L, L, M, M, S):** PLB is roughly half the stands, but not enough for everyone; every aircraft size has at least one PLB stand that can take it, and L-capable PLB stands are the scarcest.
- **~49 valid flights over 6 h (~8 per hour):** with average ground time ≈ 70 min plus a 15-minute buffer, mean demand is ~11–12 occupied stands, i.e. at or above the 11-stand capacity during the peak, so some flights **do** end up unassigned, which exercises that code path.
- **Peak bank 08:00–09:30:** mimics a morning arrival wave and makes PLB scarcity visible.
- **Size mix 30/50/20:** a realistic narrow-body-heavy mix, with enough L aircraft to stress the limited L stands.
- **Ground times by size:** bigger aircraft turn around slower.
- Targets after first run, then tune: ~5–15% unassigned, PLB rate ~50–65%. Record the final numbers in the README.

## 12. Error handling

### 12.1 Layers

| Layer | Errors | Handling |
|---|---|---|
| Startup / data files | Missing file, bad header | `DataFileError` → logged, process exits non-zero with a clear message |
| Row validation | Bad row | Never raises; produces `DataIssue` |
| Allocation | Hard-rule violation found by checker | `RuntimeError` (programming error) → fail fast at startup |
| API | Unknown stand id | `404` with the standard error body |
| API | Anything unexpected | `500` with standard error body; details logged, not leaked |
| Configuration | Invalid buffer/date/env | `ConfigError` at startup |

**Why:** *data errors* are expected and must be reported to the planner; *programming errors* must be loud. Mixing them makes both worse.

### 12.2 Standard API error body

```json
{ "error": { "code": "STAND_NOT_FOUND", "message": "Stand 'X99' does not exist." } }
```

Registered once via FastAPI exception handlers (full detail in `api-contract.md`).

## 13. Technical assumptions and trade-offs

Each assumption also goes in README §7 ("what would go wrong if false").

| ID | Assumption | If false, what goes wrong |
|---|---|---|
| A1 | Sizes are strictly ordered `S < M < L`; a stand takes any aircraft ≤ its max | Wrong fits (e.g. if a stand could take only exact sizes). Allocation would be too permissive |
| A2 | An aircraft occupies its stand for the whole `[arrival, departure)` interval; turnaround buffer applies only between consecutive occupants | If towing/pre-positioning is used, real occupancy differs; utilisation and conflicts misstated |
| A3 | Planning window defines which **arrivals** are planned (`06:00 ≤ arrival < 12:00`); departures after 12:00 are fine; arrivals outside are dropped as data issues | If the planner wants to see aircraft already on stands at 06:00, these are missing and early stands look free |
| A4 | All times are UTC; timezone-less values cannot be trusted and are rejected | If feeds are really local time without offset, many valid rows are dropped; if accepted blindly, plans shift by hours |
| A5 | For duplicate `flight_id`, the first row in file order is correct | If the later row is the correction, we keep stale data (it is still reported, so a planner can see it) |
| A6 | `departure == arrival` is invalid | A legitimately instant touch-and-go would be dropped (reported) |
| A7 | Only the first problem per row is reported | A planner may fix one error and then discover another |
| A8 | Invalid flights are excluded from `/allocations` and appear only in `/data-issues` | A consumer expecting all input rows in `/allocations` must also read `/data-issues` |
| A9 | Safe normalisation (trim, uppercase) is acceptable as a "fix" | If case is meaningful (it is not in the sample), distinct ids could merge |
| A10 | The same physical aircraft appears once per row; no linking of arrival and departure flights, no minimum turnaround per aircraft type | Real turnaround times differ by type; our buffer is one number |
| A11 | Stand availability is static for the window (no closures, no maintenance) | Allocations could use closed stands |
| A12 | Processing order = arrival, then departure, then flight id | A different priority rule gives a different (equally valid) allocation |
| A13 | Metrics use unclipped counts but clipped (to window end) occupancy minutes; buffers are not counted as occupancy | Utilisation would look higher/lower |
| A14 | Data is small (tens to hundreds of flights); O(F × S) is fine | At thousands of flights per stand, indexes or per-stand sorted structures would be needed |

### 13.1 Key trade-offs (one line each)

| Trade-off | Chosen | Reason |
|---|---|---|
| Simplicity vs optimality | Simple greedy | The PDF rewards explainability, not optimal allocation |
| Strictness vs recovery on bad rows | Drop + report, fix only trivially safe | Planning tools must not guess |
| Dependencies vs control | stdlib `csv`, no pandas | Row-accurate error reporting; fewer dependencies |
| Compute on request vs startup | Startup | Static data, deterministic, simpler API and tests |
| One-issue-per-row vs all issues | One | Keeps counts and code simple |
| In-memory vs SQLite | In-memory | Not required; fewer moving parts |
| Frontend now vs later | Later (optional) | "A strong backend with no screen scores better than a weak backend with a nice screen" |
