## 1. Project overview

Build a small, clean, well-explained Python backend that:

1. **Creates** two CSV input files (`stands.csv`, `flights.csv`) with a seeded script. The flights file deliberately contains bad rows.
2. **Loads and validates** both files. Every dropped or changed row is reported with a human-readable reason; nothing is skipped silently.
3. **Assigns a stand** to each valid flight, or marks it **unassigned with a reason**, without ever breaking the three hard rules.
4. **Exposes** the result through a small FastAPI HTTP API (`/allocations`, `/stands/{stand_id}`, `/metrics`, `/data-issues`).
5. **Computes metrics** a planner can trust, each documented (what / scope / why).
6. **Proves** the important parts with pytest tests.
7. **Documents** the work in a README that counts as much as the code, including an honest **Use of AI** section.

**What the reviewers value (from the PDF):** how you think, clarity, explaining *why*, honesty about limits. A small, clean solution you can explain beats a large one you cannot. In a follow-up call you will change the code live, so every line must be understood.

**Domain vocabulary (summary)**

| Term | Meaning |
|---|---|
| Stand | Parking spot for an aircraft |
| PLB stand | Passenger loading bridge; preferred (connected to the terminal) |
| REMOTE stand | Bus-served; works but slower/costlier |
| Ground time | Arrival → departure; the aircraft occupies the stand throughout |
| Sizes | Ordered `S < M < L`. An `S` stand takes S; `M` takes S or M; `L` takes any |

## 4. Mandatory constraints

### 4.1 Hard allocation rules (must never be broken)

| ID | Rule | Precise definition used |
|---|---|---|
| H1 | One aircraft per stand at a time | Two flights on the same stand must not have overlapping `[arrival, departure)` intervals |
| H2 | Size fit | `flight.aircraft_size <= stand.max_size` using order `S < M < L` |
| H3 | Turnaround buffer | For consecutive flights `a` then `b` on one stand: `b.arrival >= a.departure + buffer` (**exactly equal is allowed**; less is not). Default `buffer = 15 min`, configurable |

H1 is technically implied by H3 when the buffer is ≥ 0, but is tested separately because it is the most basic safety property.

### 4.2 Technical constraints

- Python ≥ 3.10; FastAPI; pytest; CSV inputs; **no database**; **no frontend** in the initial implementation; no deployment.
- Separate modules for generation, loading, validation, allocation, metrics, API (plus `config` and `models`).
- All timestamps handled as UTC (timezone-aware `datetime`; naive timestamps are rejected, never guessed).
- Invalid records are **never silently discarded**: every drop/fix appears in `/data-issues`.
- Buffer and planning window defined in **one** configuration location.
- Allocation: **simple, deterministic greedy**; explainable in an interview.
- Dependencies stay minimal (`fastapi`, `uvicorn`, `pytest`, `httpx` for the test client).

### 4.3 README must contain (9 sections)

1. What you built · 2. How to run it (Python version, install, exact commands for generate / start API / tests) · 3. Inputs (how data was created, file shapes, why these numbers) · 4. Data issues (each bad-row kind and what the code does) · 5. How allocation works (method, why, where it falls short, **one example handled badly**) · 6. Outputs and metrics · 7. Assumptions (and what breaks if false) · 8. Use of AI · 9. What you'd do next with one more day.

| Column | Type | Allowed values | Notes |
|---|---|---|---|
| `stand_id` | string | non-empty, unique | e.g. `C01`, `R03`. Trimmed and uppercased |
| `stand_type` | string | `PLB`, `REMOTE` | |

| PLB | REMOTE |
|---|---|
| C01 L, C02 L, C03 M, C04 M, C05 M, C06 S | R01 L, R02 L, R03 M, R04 M, R05 S |

### 5.2 `data/flights.csv`

| Column | Type | Allowed values | Notes |
|---|---|---|---|
| `flight_id` | string | non-empty, unique among accepted rows | Trimmed and uppercased |
| `aircraft_size` | string | `S`, `M`, `L` | `XL` and anything else is invalid |
| `arrival_time` | ISO 8601 datetime | UTC (`...Z`) | Must be within `[06:00, 12:00)` UTC on the planning date |
| `departure_time` | ISO 8601 datetime | UTC (`...Z`) | Must be strictly after arrival; **may be after 12:00** |

Planned sample: **56 rows** = 48 clean + 1 "fixable" + 7 bad. Valid flights: 49.

**Required bad rows (7 dropped kinds + 1 fixed kind, ≥ 5 required):**

| # | Kind | Example | Action |
|---|---|---|---|
| 1 | Departure before arrival | `CZ411` (from PDF) | DROPPED |
| 2 | Invalid aircraft size | `DL902,XL` (from PDF) | DROPPED |
| 3 | Missing time | `EV318` no departure (from PDF) | DROPPED |
| 4 | Malformed timestamp | `arrival_time = "15/01/2027 7pm"` | DROPPED |
| 5 | Duplicate `flight_id` | second row with an existing id | DROPPED (first kept) |
| 6 | Arrival outside planning window | arrival `05:10Z` | DROPPED |
| 7 | Missing `flight_id` | blank id | DROPPED |
| 8 | Whitespace / lower-case size | `" ax500 "`, `"m"` | FIXED (normalised), reported |

Planning date: **2027-01-15** (same as the PDF examples). Seed: **42**.

## 7. Acceptance criteria

Each criterion is checkable. IDs map to tests in `test-plan.md`.

**Data**
- AC-01 Running the generator twice yields byte-identical CSVs.
- AC-02 `flights.csv` has ≥ 5 rows that are rejected, covering ≥ 5 different issue codes.
- AC-03 Every rejected/changed row in the CSV appears in `/data-issues` with a row number, code, action and human-readable message. `rows_read = valid + dropped` holds for each file.
- AC-04 Naive (timezone-less) and malformed timestamps are rejected, not guessed.

**Allocation**
- AC-05 On the sample data and on every test scenario, `find_violations()` returns an empty list (no overlap, no size misfit, no buffer breach).
- AC-06 A gap of exactly 15 min is accepted; 14 min 59 s is rejected. The same holds for other buffer values when configured.
- AC-07 Every valid flight has exactly one allocation: assigned with a stand, or `UNASSIGNED` with a reason code and message.
- AC-08 Allocation is deterministic: same inputs → identical output.
- AC-09 On the sample data, PLB is scarce (some flights land on remote or are unassigned) and at least one flight is unassigned, so the unassigned path is demonstrated.

**API**
- AC-10 All four endpoints return the documented JSON shape and status codes.
- AC-11 `/stands/{id}` returns flights ordered by arrival; unknown id → 404 with the documented error body.
- AC-12 Changing the buffer (config or env var) and restarting changes allocations accordingly.

**Metrics**
- AC-13 ≥ 4 metrics are returned (5 planned + data-quality); each is documented in the README with what / scope / why.
- AC-14 Metric values reconcile: `assigned + unassigned = total_valid_flights`; `plb + remote = assigned`; utilisation ∈ [0, 1].

**Quality**
- AC-15 `pytest` passes from a clean checkout using the documented commands.
- AC-16 No magic numbers outside `config.py`; modules separated as required.
