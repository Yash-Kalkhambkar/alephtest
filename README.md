# Airport Stand Allocation

A Python backend that allocates aircraft stands for a morning bank of flights, exposes the result via a FastAPI HTTP API, and proves the important parts with pytest.

---

## 1. What I Built

A small, clean pipeline with five stages and a thin API layer:

```
generate_data.py  →  stands.csv + flights.csv
                              ↓
                         loader.py        (CSV → raw rows + line numbers)
                              ↓
                      validation.py       (raw rows → typed Stand / Flight + DataIssue list)
                              ↓
                      allocation.py       (valid flights + stands + buffer → Allocation list)
                              ↓
                        metrics.py        (Allocation list → 6 planner metrics)
                              ↓
                        service.py        (runs the pipeline once at startup)
                              ↓
                           api.py         (4 read-only GET endpoints)
```

Each stage is a pure function: inputs in, outputs out, no globals, no I/O except the loader and generator. This makes every function testable in isolation and easy to explain or change live.

## 2. How to Run

**Requirements:** Python 3.10 or newer.

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Generate input data (already committed; run to regenerate)
python -m stand_allocation.generate_data

# 4. Start the API
uvicorn stand_allocation.api:app --reload

# 5. Run tests
pytest
```

API available at **http://127.0.0.1:8000**. Interactive docs at **http://127.0.0.1:8000/docs**.

Endpoints:
| Method | Path | Description |
|---|---|---|
| GET | `/allocations` | All valid flights with stand or unassigned reason |
| GET | `/stands/{stand_id}` | One stand's schedule in time order |
| GET | `/metrics` | Planner metrics |
| GET | `/data-issues` | Every dropped or fixed row with reason |

## 3. Inputs

### How the data was created

Both CSV files are generated by `stand_allocation/generate_data.py` using `random.seed(42)`, so every run produces byte-identical files. The committed `data/` files were created by that script.

### `data/stands.csv` — 11 stands

| Stand | Type | Max size |
|---|---|---|
| C01, C02 | PLB | L |
| C03, C04, C05 | PLB | M |
| C06 | PLB | S |
| R01, R02 | REMOTE | L |
| R03, R04 | REMOTE | M |
| R05 | REMOTE | S |

**Why these numbers:** 6 PLB vs 5 REMOTE means PLB is roughly half the capacity, but with ~49 valid flights and average ground time ~70 min + 15 min buffer, peak demand reaches ~11–13 occupied stands — right at or above total capacity. This guarantees some flights are unassigned and PLB stands are genuinely scarce.

### `data/flights.csv` — 56 rows

- 48 clean valid flights
- 1 normalisable row (whitespace and lowercase — becomes valid after FIXED)
- 7 deliberately bad rows (details in §4)

**Why 48 clean flights:** with the 08:00–09:30 peak bank (40% of flights), stand utilisation peaks above capacity, making PLB scarcity visible and producing unassigned flights.

**Planning date:** 2027-01-15. All times UTC. Window: 06:00–12:00 UTC (arrivals only; departures may extend past 12:00).

**Size mix:** 30% S, 50% M, 20% L — narrow-body-heavy, realistic, and enough L aircraft to stress the two L-capable PLB stands.

## 4. Data Issues

The validator catches eight categories of problem. Every dropped or changed row appears in `/data-issues` with a row number, code, action, and human-readable message. Nothing is silently skipped.

| # | Kind | Issue code | Action | Example |
|---|---|---|---|---|
| 1 | Departure before arrival | `DEPARTURE_NOT_AFTER_ARRIVAL` | DROPPED | `CZ411`: arrival 09:20, departure 08:50 |
| 2 | Invalid aircraft size | `INVALID_AIRCRAFT_SIZE` | DROPPED | `DL902`: size `XL` |
| 3 | Missing required value | `MISSING_VALUE` | DROPPED | `EV318`: departure_time blank; also a row with blank flight_id |
| 4 | Malformed timestamp | `MALFORMED_TIMESTAMP` | DROPPED | `BA999`: arrival `15/01/2027 7pm` |
| 5 | Duplicate flight ID | `DUPLICATE_FLIGHT_ID` | DROPPED | Second `FL100` row ignored; first kept |
| 6 | Arrival outside window | `OUTSIDE_PLANNING_WINDOW` | DROPPED | `EA111`: arrival 05:10 (before 06:00) |
| 7 | Whitespace / lowercase | `VALUE_NORMALISED` | FIXED | `" ax500 "` → `AX500`, `" m "` → `M`; flight accepted |

**Validation order per row (first failure wins):** malformed column count → normalize → missing values → invalid size → bad timestamp → departure not after arrival → outside window → duplicate ID. First-failure-wins means one row produces one issue, keeping `rows_read = valid + dropped` exact.

**Naive timestamps** (no timezone info) are always rejected, never guessed. A timestamp like `2027-01-15T08:00:00` without a `Z` or offset is dropped with a message explaining why. Python 3.10's `datetime.fromisoformat` does not accept trailing `Z`, so we replace it with `+00:00` before parsing (Python 3.11+ handles `Z` natively).

## 5. How Allocation Works

### Method: deterministic greedy, first-come-first-served

1. Sort valid flights by `(arrival_time, departure_time, flight_id)`.
2. For each flight in that order:
   - Find **compatible stands**: `stand.max_size >= flight.aircraft_size`.
   - If none exist → `UNASSIGNED / NO_COMPATIBLE_STAND`.
   - Find **free stands**: compatible stands where `flight.arrival >= last_departure + buffer`.
   - If none are free → `UNASSIGNED / NO_STAND_AVAILABLE`.
   - **Pick** the best free stand: PLB first, then smallest sufficient size (best-fit), then stand ID alphabetically for tie-breaking.
3. Record the assignment and update that stand's last departure.

The sort is the only place that touches flight ordering. After sorting, the allocator processes each flight once in O(F × S) time — about 25 lines total.

### Why greedy and not something optimal

The PDF says optimal allocation is not expected. A greedy first-come-first-served approach is natural for operations (earliest arrival decides first, like a real queue), deterministic, O(F × S), explainable in one sentence, and easy to change live.

### Why PLB first

PLB stands are preferred but never forced. The ranking only applies among **free** compatible stands. A flight is never left unassigned while a free compatible stand exists — it falls back to REMOTE first. Priorities in order: hard rules → assign if possible → prefer PLB among options.

### Why best-fit (smallest sufficient size)

Without it, a small aircraft takes the only L-capable PLB and a large aircraft arriving minutes later has nowhere to go. Best-fit keeps large stands available for large aircraft.

### Where the algorithm falls short

1. **Myopic.** An early long-stay flight blocks a stand for many later short-stay flights.
2. **PLB-first is locally good, globally poor.** Giving PLB to the first flight may cause a later flight to end up unassigned when a different choice would have fit both.
3. **No look-ahead or backtracking.**
4. **No flight priority** (airline, passenger count, delay status).

### One example the algorithm handles badly

Only one PLB stand `C03` (M) is available:

| Flight | Size | Arrival | Departure |
|---|---|---|---|
| F1 | M | 06:00 | 10:00 (4 h) |
| F2 | M | 06:10 | 06:50 |
| F3 | M | 07:10 | 07:50 |
| F4 | M | 08:10 | 08:50 |

Greedy gives `C03` to F1 (arrives first). F2–F4 go to REMOTE. **1 of 4 flights on PLB.**

If F1 had gone to REMOTE instead, F2 → F3 → F4 could each use `C03` with 20-minute gaps. **3 of 4 flights on PLB.**

Greedy cannot see this because it never looks ahead. A fix (not implemented): rank PLB candidates by stay length, or run a swap-improvement pass after the initial allocation.

## 6. Outputs and Metrics

### Endpoints

All endpoints are read-only GET, return `application/json`, and serve from one in-memory result computed at startup.

**`GET /allocations`** — every valid flight with its stand (`ASSIGNED`) or reason code + message (`UNASSIGNED`). Sorted by arrival, departure, flight_id. Invalid/dropped flights do not appear here; they appear in `/data-issues`.

**`GET /stands/{stand_id}`** — one stand's details plus its assigned flights in arrival order, each with `gap_before_minutes` (null for the first flight) so the 15-minute rule is visible per stand. Case-insensitive lookup. Returns 404 for unknown stands.

**`GET /metrics`** — six planner metrics (see below).

**`GET /data-issues`** — every dropped or fixed row with source file, row number, record ID, issue code, action, field, original value, and human-readable message.

### Metrics

All allocation metrics cover valid flights with `arrival_time ∈ [06:00, 12:00)` UTC.

| # | Metric | What it measures | Why a planner cares |
|---|---|---|---|
| 1 | **Assignment summary** (`total_valid_flights`, `assigned`, `unassigned`, `unassigned_rate`) | How many valid flights got a stand | Unassigned aircraft need a manual solution or delay — the most urgent outcome |
| 2 | **PLB usage** (`flights_on_plb`, `flights_on_remote`, `plb_rate_of_valid`, `plb_rate_of_assigned`) | Share of flights served by a loading bridge | PLB is preferred by passengers and airlines; remote costs more and is slower |
| 3 | **Unassigned breakdown** (by reason code, by aircraft size) | Why and which flights failed | Separates capacity problems (`NO_STAND_AVAILABLE`) from infrastructure problems (`NO_COMPATIBLE_STAND`); shows if large aircraft suffer disproportionately |
| 4 | **Stand utilisation** (per stand, per type) | Share of the 360-minute window each stand is occupied | Shows idle vs overloaded stands; ground time clipped at window end; buffer gaps not counted |
| 5 | **Peak concurrency** (`aircraft_on_ground`, `first_occurred_at`, `stand_count`) | Highest number of valid aircraft on the ground at once (assigned or not) | If peak > stand count, some unassigned flights were unavoidable regardless of algorithm |
| 6 | **Data quality** (`rows_read`, `valid`, `dropped`, `fixed` per file) | Trustworthiness of the input | Tells the planner how much to trust the numbers and what to fix upstream |

**Reconciliation identities** (all verified in tests):
- `assigned + unassigned = total_valid_flights`
- `flights_on_plb + flights_on_remote = assigned`
- sum of `unassigned_breakdown.by_reason` = `unassigned`
- every `utilisation ∈ [0, 1]`
- `rows_read = valid + dropped` (per file)

## 7. Assumptions

| ID | Assumption | What goes wrong if false |
|---|---|---|
| A1 | Sizes are strictly ordered S < M < L; a stand accepts any aircraft ≤ its max | Wrong fits if a stand could only take exact sizes; allocation would be too permissive |
| A2 | An aircraft occupies its stand for the whole [arrival, departure) interval; buffer applies only between consecutive occupants | If towing or pre-positioning is used, real occupancy differs and conflicts could be misstated |
| A3 | Planning window defines which **arrivals** are planned (06:00 ≤ arrival < 12:00); departures after 12:00 are fine | Aircraft already on stands at 06:00 are invisible; early stands look free when they are not |
| A4 | All times are UTC; a timestamp with no timezone info is an error, not implicitly UTC | A naive timestamp guessed as UTC could produce a plausible-looking but wrong allocation |
| A5 | First occurrence of a duplicate flight ID wins; later occurrences are dropped | If the last row is the corrected one, the wrong version is kept |
| A6 | Zero ground time (departure == arrival) is a data error, not a valid flight | A legitimate zero-ground-time transit would be wrongly dropped |
| A7 | First validation failure per row wins; a row with two problems reports only the first | A planner sees only one issue per row; multiple fixes required per row are not visible in one pass |
| A8 | Invalid/dropped flights do not appear in `/allocations` | A planner might not realise a flight is missing; they must check `/data-issues` too |

## 8. Use of AI

**Tools used:** Claude (Anthropic) via Kiro IDE.

**What AI helped with:**

- **Planning documents** (`project-brief.md`, `technical-decisions.md`, `api-contract.md`, `test-plan.md`): AI drafted all four documents from the PDF requirements. These formed the spec before any code was written.
- **Boilerplate structure**: Initial module stubs, Pydantic schema shapes, pytest fixture patterns.
- **This README**: First draft written by AI, then reviewed and edited for accuracy.

**What I changed or rejected:**

- The initial `metrics.py` had a `rows_read` bug — it computed `valid + dropped + fixed` instead of the correct `valid + dropped` (FIXED rows are a subset of valid, not additional). Found and fixed during test writing.
- The `test_stand_not_found` test had a wrong assertion on the error code format. Fixed after the test failed.
- The `ValidationResult` dataclass was originally generic with a type parameter; simplified to plain `list` to avoid Python 3.10 compatibility issues.
- Error handling in `api.py`: AI's first version used FastAPI's default `{"detail": ...}` error shape. Replaced with the standard `{"error": {"code": ..., "message": ...}}` shape specified in the API contract.

**What I wrote or verified myself:**

- All test assertions and hand-computed expected values in `test_metrics.py` (Scenario M was worked out manually then pinned in code).
- The greedy algorithm logic and the independent `find_violations` checker — these are the core of the submission and I can explain every line.
- The buffer boundary conditions (exactly 15 min allowed, 14 min 59 s rejected).
- The `parse_utc_timestamp` helper and the Python 3.10 `Z` workaround.

**What AI got wrong:**

- Suggested using `pandas` for CSV loading. Rejected — `csv.DictReader` gives exact row numbers and full control over malformed rows.
- Initial `generate_data.py` did not snap arrival times to 5-minute intervals, producing odd times like `08:08:37`. Fixed to snap to 5-minute steps.

## 9. What I Would Do Next

With one more day:

1. **Improve the allocator** — add a swap-improvement pass after the greedy run: for each unassigned flight, check if moving any earlier assigned flight to an alternative stand would free a slot. This addresses the documented limitation without full ILP complexity.

2. **Frontend** — a simple HTML + JS page showing a per-stand Gantt timeline. The `/stands/{id}` endpoint already provides everything needed. No framework required.

3. **More validation** — stand-level checks (e.g. adjacent-stand conflicts, airline-specific gate requirements) are out of scope now but the `validate_stands` structure makes them easy to add.

4. **Parametric bad-row testing** — replace the hand-listed bad rows in `generate_data.py` with a table-driven approach so adding a new issue type is a one-line change.

5. **Richer unassigned reasons** — distinguish "no stand of the right size exists in the dataset at all" from "no stand of the right size was free at arrival time" is done; could also add "no stand of the right type (PLB-only requirement)".
